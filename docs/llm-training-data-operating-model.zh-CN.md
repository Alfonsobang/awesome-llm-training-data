# LLM 训练数据工程操作模型

这份文档描述一个面向 LLM 数据团队的实用操作模型，适用于数据采集、采购、标注、清洗、治理、评测与发布。它刻意保持保守：重点不是展示内部经验，而是让数据工作可检查、可复现、可审阅，尤其适合金融等强监管或高风险场景。

本文不依赖私有数据、专有工具或内部生产流程。

## 为什么需要操作模型

很多 LLM 数据项目的问题，并不只是缺少某个工具，而是数据工作没有被当作工程系统来管理。团队需要清楚知道：数据从哪里来、如何被处理、哪些风险被接受、质量证据如何记录，以及为什么训练或评测结果值得信任。

## 操作闭环

```mermaid
flowchart LR
    A[定义数据目标] --> B[来源与权利审查]
    B --> C[接入与标准化]
    C --> D[画像与检查]
    D --> E[过滤、去重与脱敏]
    E --> F[标注或生成]
    F --> G[质量复核与仲裁]
    G --> H[评测与泄漏检查]
    H --> I[发布、文档化与监控]
    I --> D
```

## 1. 数据目标

在采集或标注数据之前，先定义数据要完成什么任务。

- 目标模型行为：预训练、指令微调、奖励建模、检索评测、领域评测、安全评测或回归测试。
- 目标用户与场景：语言、领域、任务类型和风险等级。
- 不适用场景：私有数据还原、投资建议、绕过规则，或在缺少证据时宣称生产可用。
- 决策责任人：谁可以批准纳入、排除或发布。

清晰的数据目标可以减少后续过滤和评测决策的随意性。

## 2. 来源与权利审查

每个重要来源都应留下可见的来源记录和使用约束。

- 来源类型：公开仓库、论文数据集、benchmark、网页语料、用户贡献数据、合成数据或内部数据。
- 使用条件：许可证、服务条款、再分发限制、授权假设和下架路径。
- 采集边界：时间范围、语言、地区、文档类型、爬取范围或来源列表。
- 风险标记：个人信息、金融记录、版权内容、敏感属性或 benchmark 污染。

对于 Awesome list 中的公开资源，应优先收录官方仓库、数据集卡、论文和标准，而不是二次转述的摘要页面。

## 3. 接入与标准化

数据接入既要保留证据，也要让数据可用。

- 在合法且可行的前提下，保留原始来源引用或哈希。
- 标准化 schema、编码、文档 ID、时间戳和语言元数据。
- 区分内容字段和元数据字段。
- 记录处理版本，使下游行为变化可以被解释。

团队应避免使用会静默覆盖来源记录的一次性脚本。

## 4. 画像与检查

数据质量工作同时需要统计信号和人工检查。

- 整体画像：语言分布、来源分布、长度、token 数、重复率、空字段、敏感信息命中和格式错误。
- 分片画像：领域、任务类型、来源家族、时间段、语言、标签、风险类别和难度。
- 人工检查：抽查高占比分片、稀有分片、异常值和新增来源。
- 漂移审查：将新版本与历史版本进行对比。

画像不能替代判断，但可以告诉评审者哪里最需要判断。

## 5. 过滤、去重与脱敏

过滤决策应尽量显式、可解释，并在可能时可回溯。

- 记录过滤器名称、版本、阈值和排除数量。
- 区分精确重复、近似重复、模板噪声和语义重叠。
- 将隐私脱敏与质量过滤分开记录。
- 在允许的情况下，保留被排除样本的代表性例子供审计使用。
- 注意过度过滤可能删除稀有但重要的领域样本。

在高风险领域，排除标准应在发布前与法务、隐私或治理相关角色一起审查。

## 6. 标注或生成

人工标注和合成数据生成都需要质量控制。

- 标注规范：任务定义、边界案例、跳过规则、平局规则和示例。
- 标注校准：试标批次、评审讨论、一致性或分歧复核，以及仲裁。
- 合成生成：生成模型、提示词、采样设置、过滤规则和来源字段。
- 偏好数据：prompt、候选回答、偏好标签、平局或跳过状态、标注者或裁判模型元数据，以及 rejected response 是否可用。

合成数据应保留合成来源。不要在没有 provenance 的情况下把它混入人工数据。

## 7. 质量复核与仲裁

质量复核应关注错误模式，而不仅是平均分。

- 复核分歧集群和模糊案例。
- 追踪标注者或评审者随时间发生的漂移。
- 区分规范问题和执行错误。
- 同时抽查被接受和被拒绝的样本。
- 用明确的局限性说明替代单一质量分数。

对于 LLM 数据工作，一份简短的仲裁说明往往比没人看的大型仪表盘更有价值。

## 8. 评测与泄漏检查

评测数据必须与训练数据决策隔离。

- 检查训练、微调、验证和测试集之间的精确重复与近似重复。
- 在需要时按来源、时间、实体、文档家族或任务家族切分。
- 避免在合成数据提示词中使用 benchmark 答案或解析。
- 说明某个数据集适合开发、验证、最终报告，还是只适合探索性分析。
- 在金融领域评测中，区分知识、推理、合规、幻觉、检索可溯源性和拒答行为。

benchmark 不是生产可用性的证明。

## 9. 发布、文档化与监控

数据集发布应包含足够上下文，让另一个团队能够理解并复现相关决策。

- 数据集卡、datasheet 或 README。
- 版本历史和主要变化。
- 已知局限性和预期用途。
- 许可证与访问说明。
- 已完成和未完成的质量检查。
- issue tracker、维护者联系方式或废弃路径。

在内部或强监管场景下，还应记录审批证据以及隐私和合规审查状态。

## 轻量成熟度分级

| 等级 | 描述 | 常见证据 |
| --- | --- | --- |
| 0 | 临时数据工作 | 一次性文件、来源历史不清、没有复核轨迹 |
| 1 | 来源已文档化 | 基本 provenance、许可证和 schema 说明 |
| 2 | 可重复处理 | 版本化脚本、画像报告、去重和过滤日志 |
| 3 | 质量已审查 | 标注 QA、仲裁记录、泄漏检查和风险审查 |
| 4 | 生命周期治理 | 发布标准、监控、废弃机制和跨职能责任人 |

多数团队不需要一开始就达到 4 级。从 0 级推进到 2 级，已经能避免很多昂贵错误。

## 维护者自查问题

- 评审者能否解释这批数据为什么存在？
- 团队能否复现同一个数据集版本？
- 团队能否找到版本之间发生了什么变化？
- 质量问题是否能按分片暴露，而不只是一个全局指标？
- 隐私、权利和合规约束是否在训练前被记录？
- 评测数据是否避免了训练泄漏和合成污染？
- 数据集是否真的对模型或评测团队有用，而不只是看起来丰富？
